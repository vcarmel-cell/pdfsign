# PDFSign — מילוי טפסי PDF וחתימה דיגיטלית

אפליקציית דף-אינטרנט סטטית (בלי שרת, בלי build) שמאפשרת להעלות מסמכי PDF, לסמן עליהם היכן צריך למלא נתונים ולחתום, ולשלוח קישור לשותפים שממלאים וחותמים כל אחד עותק משלו.

- `admin.html` — ניהול: התחברות, העלאת תבניות, סימון שדות, קישורי שיתוף, צפייה בהגשות.
- `fill.html?id=...` — הדף שהשותפים פותחים כדי למלא ולחתום.

כל הלוגיקה רצה בדפדפן. Firebase (Firestore + Auth + Storage) משמש כאחסון משותף, ו-EmailJS שולח התראת מייל (כולל צירוף/קישור ל-PDF החתום) בכל הגשה — בלי Cloud Functions. שימוש ב-Firebase Storage **דורש שדרוג לתוכנית בתשלום (Blaze)**, גם אם בפועל צורכים רק כמויות זעירות בחינם.

**חשוב להבין:** קובצי PDF של תבניות/הגשות **חדשות** נשמרים ב-Firebase Storage, עם מגבלת **3MB לקובץ**. תבניות/הגשות **ישנות** (שהועלו לפני שהאפליקציה עברה ל-Storage) ממשיכות להישמר ולעבוד בדיוק כמו קודם — כמחרוזת Base64 בתוך מסמך Firestore עצמו, מוגבלות לכ-500KB — בלי צורך במיגרציה; שני הפורמטים נתמכים זה לצד זה לצמיתות.

## הקמה (חד פעמי)

### 1. פרויקט Firebase חדש
ב-[console.firebase.google.com](https://console.firebase.google.com) → Add project → צרו פרויקט ייעודי חדש (לא לחבר לפרויקט קיים אחר בשימוש).

**שדרגו את הפרויקט לתוכנית Blaze** (Upgrade project → Blaze, בתחתית התפריט הצדדי) — Firebase Storage לא זמין בתוכנית החינמית (Spark) אפילו בשימוש אפס. תוכנית Blaze היא תשלום-לפי-שימוש עם נדבך חינמי נדיב; אפליקציה בהיקף כזה צפויה להישאר בפועל בעלות אפסית.

בתוך הפרויקט הפעילו:
- **Authentication** → Sign-in method → הפעילו **Email/Password** וגם **Anonymous**.
- **Firestore Database** → Create database → מצב Production.
- **Storage** → Get started → מצב Production (אותו אזור/מיקום כמו ה-Firestore, לנוחות).

### 2. יצירת משתמש המנהל
Authentication → Users → Add user → הזינו `v.carmel@gmail.com` וסיסמה לבחירתכם. זהו חשבון המנהל היחיד; אין הרשמה עצמית באפליקציה.

### 3. חוקי אבטחה
- Firestore → Rules → העתיקו לשם את תוכן הקובץ `firestore.rules` ולחצו Publish. (חוקי ה-Firestore כוללים גם בדיקת גודל על שדה ה-PDF הישן, כדי שמסמך שחורג מהמכסה יידחה בצד השרת ולא רק בצד הלקוח.)
- Storage → Rules → העתיקו לשם את תוכן הקובץ `storage.rules` ולחצו Publish. שני קבצי החוקים האלה **לא** מתעדכנים אוטומטית מה-repo — כל שינוי עתידי בהם דורש להעתיק-להדביק שוב ידנית.

### 4. חיבור האפליקציה לפרויקט
Project settings → General → Your apps → הוסיפו אפליקציית Web → העתיקו את אובייקט הקונפיג שמתקבל (`apiKey`, `authDomain`, `storageBucket` וכו') לתוך `js/firebase-init.js`, במקום הערכים ש-`PASTE_...`.

### 5. EmailJS (למייל התראה + צירוף ה-PDF החתום בכל הגשה)
1. הרשמו בחינם ב-[emailjs.com](https://www.emailjs.com).
2. Email Services → חברו שירות מייל (למשל Gmail) → קבלו **Service ID**.
3. Email Templates → צרו תבנית עם המשתנים: `{{template_name}}`, `{{filler_name}}`, `{{submitted_at}}`, וגם **`{{pdf_link}}`** (קישור הורדה ישיר לעותק החתום ב-Firebase Storage — מתמלא רק כשההגשה נשמרה דרך Storage, לא עבור תבניות ישנות; מומלץ להוסיף אותו כקישור בגוף התבנית). **חשוב:** בהגדרות התבנית עצמה שדה "To Email" חייב להיות `{{to_email}}` — אחרת המייל לא יישלח לכתובת הדינמית ולא תופיע שגיאה.
4. באותה תבנית, עברו ללשונית **Attachments** → הוסיפו צירוף מסוג **Variable Attachment** → תנו לו את שם המשתנה `pdf_attachment` וסוג תוכן PDF. (המגבלה בתוכנית החינמית של EmailJS היא כ-500KB לצירוף, נמוכה ממגבלת ה-3MB של הקובץ עצמו — זו הסיבה ש-`{{pdf_link}}` קיים כגיבוי: כשהקובץ גדול מדי לצירוף, הקישור עדיין מגיע.)
5. קבלו **Template ID**, ומתחת ל-Account → General את ה-**Public Key**.
6. הזינו את שלושת הערכים ב-`js/firebase-init.js` תחת `EMAILJS_CONFIG`.

אם משאירים את `EMAILJS_CONFIG.publicKey` כ-`PASTE_...`, האפליקציה תמשיך לעבוד רגיל (הגשות נשמרות כרגיל ב-Firestore) — רק שליחת המייל תדולג בשקט.

### 6. זיהוי שדות אוטומטי (AI) — Gemini + Cloud Function
תכונה אופציונלית: זיהוי אוטומטי של שדות למילוי בתבנית PDF, ע"י מודל Gemini (Google) שמנתח את תמונות העמודים ומציע שדות טיוטה (שעדיין ניתנים לעריכה/מחיקה לפני שמירה). זו הפעם הראשונה שהאפליקציה משתמשת ברכיב שרת (Cloud Function) — כי מפתח ה-API של Gemini חייב להישאר בצד שרת ולא להיחשף בקוד הלקוח.

1. קבלו מפתח Gemini API בחינם (בלי כרטיס אשראי) ב-[aistudio.google.com/app/apikey](https://aistudio.google.com/app/apikey).
2. התקינו Firebase CLI אם עוד לא מותקן (`npm install -g firebase-tools`), ומהתיקייה הראשית של הפרויקט (`PDFSign/`) התחברו: `firebase login`.
3. ודאו שהפרויקט הנכון נבחר (`.firebaserc` כבר מצביע על `pdfsign-b5230`; `firebase use pdfsign-b5230` אם צריך).
4. שמרו את מפתח ה-API ב-Secret Manager: `firebase functions:secrets:set GEMINI_API_KEY` (יבקש להדביק את המפתח).
5. פרסו את הפונקציה: `firebase deploy --only functions`.
6. בסוף הפריסה יודפס URL של הפונקציה (למשל `https://us-central1-pdfsign-b5230.cloudfunctions.net/detectFields`) — העתיקו אותו לתוך `js/firebase-init.js`, בקבוע `AI_DETECT_FUNCTION_URL`, במקום `PASTE_...`.
7. מתן גישה למשתמש: במסך "ניהול משתמשים" לחצו "הפוך לפרימיום" ליד המשתמש הרצוי — רק מנהל ומשתמשי פרימיום רואים את כפתור "זיהוי שדות אוטומטי (AI)" בעורך השדות. זה דגל ידני בלבד שהמנהל קובע — אין חיוב/מנוי בפועל.

התכונה כולה אופציונלית: אם `AI_DETECT_FUNCTION_URL` נשאר `PASTE_...`, הכפתור פשוט לא מוצג, ושאר האפליקציה ממשיכה לעבוד רגיל. **חשוב:** אם מפתח ה-API מתחלף בעתיד (`functions:secrets:set` שוב), צריך גם לפרוס מחדש (`firebase deploy --only functions`) כדי שהפונקציה תשתמש בערך החדש — עדכון הסוד לבדו לא מספיק.

### 7. שליחת הזמנות בקבוצה (Excel) — Gmail + Cloud Function
תכונה אופציונלית נוספת: מנהל/משתמש פרימיום מעלה קובץ Excel עם שמות ואימיילים לתבנית מסוימת (מצב חתימה יחידה בלבד), וכל מי שברשימה מקבל מייל עם **אותו קישור שיתוף רגיל** של התבנית (אין מעקב אחר מי כבר מילא). זו הפונקציה השנייה שהאפליקציה מפרסת (`sendBulkInvites`, לצד `detectFields`) — שתיהן נפרסות יחד עם אותה פקודת `firebase deploy --only functions`, אין צורך בהגדרה נפרדת.

**חשוב:** בניגוד ל-Gemini, כאן **כל משתמש (מנהל/פרימיום) מגדיר את חשבון ה-Gmail שלו בעצמו** — אין מפתח משותף אחד. זה נעשה עצמאית בתוך `admin.html`, בלי מעורבות של מנהל-העל:
1. המשתמש מפעיל אימות דו-שלבי בחשבון ה-Google שלו (myaccount.google.com/security), אם עוד לא מופעל.
2. יוצר App Password (קוד בן 16 תווים, שונה מהסיסמה הרגילה) ב-[myaccount.google.com/apppasswords](https://myaccount.google.com/apppasswords).
3. במסך "תבניות" ב-`admin.html`, פותח את "שליחת הזמנות דרך Gmail - הגדרה" ומזין שם את כתובת ה-Gmail וה-App Password. נשמר ב-Firestore תחת `gmailSenders/{uid}` (אוסף נפרד מ-`users/{uid}`, עם הרשאות קריאה/כתיבה מוגבלות לבעלים/מנהל בלבד — לא לכל מחובר).

הגדרה חד-פעמית מהצד שלכם (בעל האפליקציה):
1. אחרי הוספת `sendBulkInvites` ל-`functions/index.js`, פרסו: `firebase deploy --only functions`.
2. העתיקו את ה-URL שיודפס לתוך `js/firebase-init.js`, בקבוע `BULK_INVITE_FUNCTION_URL`, במקום `PASTE_...`.

הגישה לתכונה נשלטת ע"י אותו דגל "פרימיום" שכבר קיים לזיהוי השדות האוטומטי — אין הגדרה נפרדת. מוגבל ל-**100 נמענים בכל שליחה** (חשבון Gmail אישי מוגבל בעצמו לכ-500 מיילים ביום, וזה משאיר מרווח לשימוש הרגיל בחשבון ולמניעת חסימה כתוצאה משליחה מרוכזת).

### 8. בדיקה מקצה לקצה
1. פתחו את `admin.html`, התחברו.
2. העלו PDF קטן לדוגמה (מתחת ל-3MB), תנו לו שם.
3. בעורך השדות: בחרו סוג שדה (טקסט/תאריך/תיבת סימון/חתימה) וגררו מלבן על המסמך במקום הרצוי. שמרו שדות.
4. העתיקו את קישור השיתוף ופתחו אותו בטאב/דפדפן אחר (או בטלפון) כאילו אתם שותף.
5. מלאו את כל השדות, חתמו (עכבר או אצבע), שלחו.
6. חזרו ל-`admin.html` → "הגשות" → ודאו שההגשה מופיעה, שאפשר להוריד ממנה PDF, ושהוא מציג את הטקסט והחתימה בדיוק במקומות שסומנו. בדקו גם שהגיע מייל עם הקובץ מצורף.
7. פתחו את אותו קישור שיתוף בפעם נוספת כ"שותף אחר" — ודאו שנוצרת הגשה נפרדת נוספת (הקישור אינו חד-פעמי).

## תפקידים: מנהל ומשתמשים

יש שני סוגי חשבונות:
- **מנהל-על** — תמיד `v.carmel@gmail.com` (מוגדר קשיח בקוד ובחוקי האבטחה, לא ניתן לשינוי דרך הממשק). רואה ומנהל את **כל** התבניות וההגשות של כל המשתמשים, ובנוסף יכול ליצור/לבטל גישה למשתמשים דרך מסך "ניהול משתמשים" (מופיע רק אצלו).
- **משתמשים** — נוצרים ע"י המנהל (מסך "ניהול משתמשים" → אימייל + סיסמה זמנית). כל משתמש רואה ומנהל **רק** את התבניות וההגשות שהוא עצמו יצר, ויכול לשלוח קישורי מילוי ללקוחות שלו באופן עצמאי. אחרי הכניסה הראשונה, המשתמש יכול לשנות את הסיסמה הזמנית בעצמו (מסך "תבניות" → "שינוי סיסמה").

**"ביטול גישה" למשתמש לא מוחק את חשבון ה-Auth שלו** (אין ל-client-side גישה למחיקת חשבונות משתמשים אחרים בלי Admin SDK) — זה רק מסיר ממנו את ההרשאה להשתמש באפליקציה, באופן מיידי (גם אם הטאב שלו כבר פתוח). "הפעלה מחדש" מחזירה גישה לאותו חשבון בדיוק, בלי צורך ליצור אותו מחדש.

**חשוב לאחר השדרוג הראשון**: תבניות שנוצרו *לפני* הוספת מערכת המשתמשים לא היו שייכות לאף אחד באופן מפורש. בפעם הראשונה שהמנהל-על נכנס ל-`admin.html` אחרי השדרוג, האפליקציה "מאמצת" אוטומטית את כל התבניות הישנות האלה אליו (שיוך `ownerId`). **מומלץ להיכנס כמנהל פעם אחת מיד אחרי פרסום הגרסה הזו**, לפני שמישהו אחר מנסה למלא קישור לתבנית ישנה — אחרת מילוי טופס כזה עלול להיכשל עד שהמנהל יתחבר בפעם הראשונה.

## מסמך רב-חותמים (כמה אנשים חותמים על אותו מסמך משותף)

בנוסף למצב הרגיל (כל שותף/לקוח ממלא עותק עצמאי משלו), אפשר להגדיר תבנית כ**מסמך רב-חותמים**: מספר קבוע מראש של תפקידי חתימה (למשל "עובד", "מנהל", "עד"), כשכל חותם רק מזין את שמו וחותם, וכל חותם רואה את החתימות של מי שחתם לפניו כבר על גבי המסמך.

**איך זה עובד:**
1. בעורך השדות, סמנו את "מסמך רב-חותמים". כל שדה חתימה בתבנית הופך לתפקיד — **שם השדה (בתיבת הטקסט שבכותרת השדה) הוא שם התפקיד** שיוצג לחותם.
2. לחצו "התחלת סבב חתימות חדש" — זה פותח סבב חדש, ריק.
3. במסך "הגשות" של התבנית תראו את הסבב, עם כפתור "העתקת קישור" נפרד לכל תפקיד שעדיין לא חתם. שלחו לכל אדם את הקישור המתאים לתפקיד שלו.
4. כל חותם ממלא את השדות המשותפים (רק אם עדיין לא מולאו ע"י חותם קודם) וחותם. אחרי החתימה האחרונה, ה-PDF הסופי נוצר אוטומטית עם כל החתימות, נשמר, ונשלחת התראת מייל **פעם אחת** (לא בכל חתימה בנפרד).
5. אפשר לפתוח סבבים חדשים ונפרדים על אותה תבנית שוב ושוב (למשל לחוזה כזה עם עובד אחר בכל פעם) — כל סבב עצמאי לחלוטין.

**מגבלות שכדאי לדעת:**
- אי אפשר להחליף בין "מצב רגיל" ל"מסמך רב-חותמים" בזמן שיש סבב פעיל על התבנית (הבחירה נחסמת עד שהסבב מסתיים).
- אם החותם האחרון סוגר את הדפדפן/מאבד רשת בדיוק בין רגע השלמת הסבב לשמירת ה-PDF הסופי (מצב נדיר), הסבב עלול "להיתקע" עם סטטוס "משלים...". במקרה כזה יופיע כפתור "נסה שוב להשלים" בשורת ההגשה — הוא בונה מחדש את ה-PDF הסופי מהנתונים שכבר נשמרו (בטוח להריץ, לא משנה נתונים).

## מגבלות ומכסות (משתמשים רגילים בלבד — למנהל-העל אין הגבלה)

- **עד 10 תבניות** למשתמש. יש למחוק תבנית ישנה כדי להוסיף חדשה מעבר לכך.
- **עד 99 הגשות** סה"כ (על פני כל התבניות של המשתמש). יש למחוק הגשות ישנות כדי להמשיך לקבל הגשות חדשות — כשהמכסה מלאה, מי שמנסה למלא טופס רואה הודעה שהטופס לא מקבל הגשות כרגע.
- בכל תבנית ברשימה מוצג מספר ההגשות שהתקבלו עבורה, ובמסך ההגשות של תבנית יש כפתור "הורדת כל ההגשות (ZIP)" שאורז את כולן לקובץ ZIP אחד.

## הערות טכניות

- תבנית PDF שהועלתה היא **בלתי ניתנת להחלפה** — כדי לעדכן מסמך יוצרים תבנית חדשה (כדי שמיקומי השדות, שנשמרים כאחוזים מגודל העמוד, לא "יזוזו" ביחס למסמך חדש).
- טקסט שהמשתתף מקליד (כולל עברית) מוטבע ב-PDF כתמונה שנוצרת בדפדפן (canvas), ולא כטקסט PDF רגיל — כך נמנעת בעיית קידוד גופנים בעברית מול הגופנים הסטנדרטיים של pdf-lib.
- אם המסמך החתום הסופי (אחרי הטבעת הטקסט והחתימה) חורג מהמכסה למרות שהתבנית המקורית הייתה בתוך הגבול, ההגשה עדיין נשמרת ב-Firestore (בלי עותק PDF), והמערכת מזהירה את השותף במסך ההצלחה להוריד עותק אישי מיד — כדי שלא יאבד.
- אין כלי בדיקות אוטומטיות בפרויקט הזה (כמו שאר התיקיות בסביבת העבודה) — הבדיקה היא ידנית לפי הצעדים בסעיף 6.
